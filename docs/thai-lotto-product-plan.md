# แผนพัฒนาโปรเจกต์เว็บช่วยหาเลขหวยไทย

## 1. ภาพรวมของโปรเจกต์
โปรเจกต์นี้ถูกปรับแนวคิดจากเว็บสุ่มเลขแนวเกม ให้เป็นเว็บช่วยหาเลขหวยไทยที่อิงพฤติกรรมผู้ใช้จริงมากขึ้น คือ:
- อยากได้เลขเร็ว
- อยากรู้ที่มาของเลข
- ไม่อยากสมัครสมาชิก
- อยากเก็บโพยไว้เอง
- อยากตีเลขจากความฝันหรือสิ่งที่พบเจอ

หลักคิดของ MVP นี้คือ `frontend-only`, `no database`, `no auth`, และ `rule-based logic` เพื่อให้ปล่อยของได้เร็ว ควบคุม behavior ได้ง่าย และยังอธิบายเหตุผลของเลขที่สร้างออกมาได้

## 2. เป้าหมายของเวอร์ชันปัจจุบัน
### เป้าหมายเชิงโปรดักต์
- เปลี่ยน positioning ของเว็บให้ชัดว่าเป็น “ผู้ช่วยหาเลข” ไม่ใช่เครื่องสุ่มเลขเล่น ๆ
- ทำ flow หลักให้ใช้งานได้จริงบนมือถือในไม่กี่คลิก
- ทุกผลลัพธ์ต้องมีที่มาของเลข ไม่ใช่โยนเลขอย่างเดียว
- ผู้ใช้ต้องเก็บโพยและแชร์ต่อได้โดยไม่ต้องสมัครสมาชิก

### เป้าหมายเชิงเทคนิค
- ใช้โครงสร้างข้อมูลกลางสำหรับผลลัพธ์ทุกโหมด
- ใช้ localStorage เป็นที่เก็บโพยและประวัติ
- ใช้ static JSON เป็นฐานข้อมูลกฎและผลย้อนหลัง
- แยก logic การตีเลขออกจาก UI เพื่อให้ขยายได้ในรอบถัดไป

## 3. สิ่งที่ทำเสร็จแล้ว
ด้านล่างคือสิ่งที่ implement แล้วในรอบนี้

### 3.1 Product reset และ UX reset
ทำแล้ว:
- เปลี่ยนหน้าแอปหลักจาก Lucky Number Generator เป็นหน้าเว็บแนว “Thai Lotto Idea Helper”
- เปลี่ยน hero section, copywriting, CTA และ visual tone ให้เข้ากับบริบทหวยไทย
- ตัดองค์ประกอบแนวคาสิโนและ gimmick ที่ไม่ช่วย core value ออก
- ใส่ disclaimer ให้ชัดว่าใช้เพื่อไอเดียเลขและความบันเทิง ไม่ได้การันตีผล

สถานะ:
- ใช้งานได้แล้ว
- เหมาะเป็น MVP หน้าเดียวแบบ mobile-first

### 3.2 Quick Pick
ทำแล้ว:
- รองรับการสุ่มเลข `2 ตัว`, `3 ตัว`, `6 ตัว`
- เลือกจำนวนชุดได้
- ล็อกบางหลักได้
- ตัดเลขที่ไม่ต้องการออกได้
- เก็บผลลัพธ์ล่าสุดไว้ใน recent slips
- สร้างคำอธิบายประกอบว่าโพยนี้ถูกสร้างจากเงื่อนไขอะไร

สถานะ:
- ใช้งานได้แล้ว
- มีการกัน loop สุ่มไม่จบด้วย attempt limit ใน engine

### 3.3 Dream to Number
ทำแล้ว:
- รับข้อความความฝันแบบ free text
- ใช้ `dream-rules.json` เป็น dictionary rule-based
- ดึง keyword ที่ match จากข้อความ
- ดึงตัวเลขที่อยู่ในข้อความ เช่น “ตี 2”
- สร้างเลขเด่น, เลข 2 ตัว, 3 ตัว, 6 ตัว
- สร้างเหตุผลอธิบายที่มาของเลข

สถานะ:
- ใช้งานได้แล้ว
- ยังเป็น keyword matching แบบ deterministic

### 3.4 Story to Number
ทำแล้ว:
- รับข้อความเหตุการณ์หรือสิ่งที่พบเจอ
- ใช้ `symbol-rules.json` สำหรับสัตว์, สี, รถ, บ้าน, ทะเบียน, ใบเสร็จ
- ดึงเลขตรงจากข้อความ เช่น `287`
- ดึงเลขจากเวลา เช่น `11:11`
- รวมผลจาก keyword กับ digit extraction เพื่อสร้างโพย

สถานะ:
- ใช้งานได้แล้ว
- ตอนนี้ยังเป็น parser แบบง่าย ยังไม่ได้มี NLP หรือ weighting ที่ซับซ้อน

### 3.5 Saved Picks และ Share
ทำแล้ว:
- บันทึกโพยด้วย `localStorage`
- เก็บ recent generations และ saved slips แยก key ชัดเจน
- แชร์โพยด้วย Web Share API
- fallback เป็น clipboard หาก browser ไม่รองรับ share

สถานะ:
- ใช้งานได้แล้ว
- เหมาะกับแนวคิด “ไม่ต้องสมัครสมาชิก”

### 3.6 Results History
ทำแล้ว:
- เพิ่ม `lottery-results.json` เป็น static dataset ภายในโปรเจกต์
- แสดงรางวัลที่ 1, เลขท้าย 2 ตัว, หน้า 3 ตัว, ท้าย 3 ตัว
- คัดลอกเลขรางวัลที่ 1 ได้

สถานะ:
- ใช้งานได้แล้ว
- ยังเป็นชุดข้อมูลตัวอย่าง ไม่ใช่ข้อมูล production จริง

### 3.7 Technical foundation
ทำแล้ว:
- เพิ่ม `src/lib/lotteryEngine.js`
- เพิ่ม `src/lib/storage.js`
- เพิ่ม data files แยกเป็น `dream-rules.json`, `symbol-rules.json`, `lottery-results.json`
- กำหนด shape กลางของผลลัพธ์ในรูป `GeneratedSlip`
- build และ lint ผ่านแล้ว

## 6. ข้อจำกัดของเวอร์ชันปัจจุบัน
### Product limitations
- ยังไม่มีเลขจากข้อมูลส่วนตัว เช่น วันเกิด ทะเบียนรถ เบอร์โทร
- ยังไม่มี trend “เลขมาแรง” ของผู้ใช้ทั้งระบบ
- ยังไม่มีหน้าแยกหลายหน้า ยังเป็นหน้าเดียวแบบ section-based
- ยังไม่มี share เป็นรูปภาพ

### Data limitations
- dream rules และ symbol rules ยังมีจำนวน keyword น้อย
- ยังไม่มีระบบจัดน้ำหนัก rule หรือ priority ระหว่างหลาย keyword
- ผลย้อนหลังเป็นตัวอย่าง static data ไม่ได้อัปเดตอัตโนมัติ

### Technical limitations
- ไม่มี backend
- ไม่มี analytics
- ไม่มี moderation
- ไม่มี notification
- ไม่มี AI หรือ NLP ขั้นสูง

## 7. แผนงานถัดไป
ด้านล่างคือ roadmap ที่ควรทำเพิ่ม โดยจัดเรียงตามลำดับความคุ้มค่าและความเสี่ยง

### Phase 1.1: เก็บคุณภาพของ MVP ที่มีอยู่
เป้าหมาย:
- ทำให้ของที่มีอยู่ตอนนี้แน่นขึ้นก่อนเพิ่ม scope

สิ่งที่ควรทำ:
- ปรับข้อความภาษาไทยใน UI ให้คมและสม่ำเสมอทุกจุด
- เพิ่ม validation ให้ละเอียดขึ้น เช่น กรณีล็อกเลขครบทุกหลักจนเหลือจำนวนชุดไม่พอ
- ปรับ UX ของ saved slips ให้เลือกดูโพยเดิมได้ ไม่ใช่มีแต่แชร์
- แสดง empty states และ helper text ให้ชัดขึ้น
- เพิ่มการเรียง recent slips/saved slips ที่สื่อสารง่ายกว่าเดิม

ความยาก:
- ต่ำ

ทำได้จริงไหม:
- ทำได้ทันที

เครื่องมือ:
- React
- localStorage
- CSS

### Phase 1.2: เพิ่มเลขจากข้อมูลส่วนตัว
เป้าหมาย:
- รองรับพฤติกรรมจริงของคนเล่นหวยไทยที่ชอบเอาเลขวันเกิด ทะเบียนรถ บ้านเลขที่ หรือเบอร์โทรมาตี

สิ่งที่ควรทำ:
- เพิ่ม section ใหม่ `Personal Numbers`
- รับข้อมูลต่อไปนี้อย่างน้อย:
  - วันเกิด
  - ปีเกิด
  - บ้านเลขที่
  - ทะเบียนรถ
  - เบอร์โทร
- สร้างกฎแปลงข้อมูลเป็นเลขเด่น
- เพิ่ม preset เช่น:
  - เน้นเลขท้าย
  - เน้นเลขเบิ้ล
  - เน้นเลขมงคล
- ใช้ output shape เดิมของ `GeneratedSlip`

ความยาก:
- กลาง

ทำได้จริงไหม:
- ทำได้จริงมาก และไม่ต้องใช้ database

เครื่องมือ:
- React form state
- utility parse string/number
- local rule engine

### Phase 1.3: ทำผลย้อนหลังให้ใกล้ของจริงขึ้น
เป้าหมาย:
- เปลี่ยนผลย้อนหลังจาก example dataset เป็นข้อมูลที่น่าใช้งานจริงมากขึ้น

สิ่งที่ควรทำ:
- ขยาย dataset ให้มีหลายงวดมากขึ้น
- เพิ่ม schema ถ้าต้องใช้ เช่น:
  - `nearPrize`
  - `drawYear`
  - `sourceUrl`
- ทำ summary cards เช่น:
  - เลขท้าย 2 ตัวล่าสุด
  - เลขที่เคยออกบ่อยใน dataset
  - เลขที่ไม่ออกนานใน dataset
- ถ้าจะใช้ข้อมูลจริง ควรมีสคริปต์นำเข้าเป็นรอบ ๆ แต่ยังไม่ต้องมี database

ความยาก:
- กลาง

ทำได้จริงไหม:
- ทำได้จริง

เครื่องมือ:
- static JSON
- script สำหรับเตรียม data ในภายหลัง

### Phase 1.4: ขยาย rule engine
เป้าหมาย:
- ทำให้การตีเลขมีความสมจริงและหลากหลายขึ้น

สิ่งที่ควรทำ:
- เพิ่มจำนวน keyword ใน `dream-rules.json`
- เพิ่มจำนวน keyword ใน `symbol-rules.json`
- เพิ่ม concept ของ weight หรือ confidence score
- แยกเลขตรงจากข้อความ กับเลขตีความจาก keyword ให้ชัดกว่าเดิม
- เพิ่ม rule สำหรับ:
  - สี
  - อารมณ์
  - สถานที่
  - เวลา
  - จำนวนคน/สัตว์
- เพิ่ม priority logic เมื่อข้อความมีหลาย keyword

ความยาก:
- กลางถึงสูง

ทำได้จริงไหม:
- ทำได้จริง แต่ต้องใช้เวลา curate data rules

เครื่องมือ:
- JSON rules
- utility functions
- optional test cases สำหรับ engine

## 8. ลำดับความสำคัญที่แนะนำ
ถ้าจะทำต่อทันที ควรเรียงแบบนี้:

1. เก็บคุณภาพ MVP ที่มีอยู่
2. เพิ่มเลขจากข้อมูลส่วนตัว
3. ขยายผลย้อนหลังและทำ summary จาก static dataset
4. ขยาย rule engine ให้ฉลาดขึ้น
5. ทำ share เป็นภาพ
6. ค่อย refactor เป็นหลาย modules/หลายหน้า

เหตุผล:
- ลำดับนี้เพิ่ม value ให้ผู้ใช้เร็วที่สุด
- ยังไม่ดึงโปรเจกต์เข้าสู่ความซับซ้อนของ backend
- ยังรักษาหลัก “เร็ว ใช้ง่าย ไม่ต้องสมัคร” ไว้ได้

## 9. สิ่งที่ยังไม่ควรทำตอนนี้
- ระบบสมาชิก
- database
- community
- comment/reaction
- notification push
- analytics ฝั่ง server
- recommendation personalization แบบจริงจัง
- AI วิเคราะห์ข้อความแบบ production

เหตุผล:
- ไม่ตรงกับ pain หลักของผู้ใช้ในระยะแรก
- เพิ่มต้นทุนและ complexity สูง
- ทำให้เสียความเร็วในการปล่อย MVP

## 10. หลักการสื่อสารที่ต้องคงไว้
- ใช้คำว่า “ไอเดียเลข”
- ใช้คำว่า “เพื่อความบันเทิง”
- หลีกเลี่ยงคำว่า “แม่น” และ “การันตี”
- ถ้าใช้ผลย้อนหลัง ต้องอธิบายว่าเป็นข้อมูลในอดีต
- ถ้าใช้ข้อมูลจริงในอนาคต ควรระบุแหล่งอ้างอิงให้ชัด

## 11. สรุปสั้น
ตอนนี้โปรเจกต์เดินมาถูกทางแล้วในระดับ MVP:
- product positioning ถูกรีเซ็ตแล้ว
- flow หลัก 3 แบบใช้งานได้แล้ว
- save/share/history มีแล้ว
- data และ engine ถูกแยกออกจาก UI แล้ว

สิ่งที่ควรทำต่อไม่ใช่การเพิ่ม backend แต่คือ:
- ทำให้ rule engine แน่นขึ้น
- เติมเลขจากข้อมูลส่วนตัว
